## 三、发现的缺陷（6 处）

### 缺陷 1 · `pip install -r requirements.txt` 在中文 Windows 上直接失败 🔴 阻塞级

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xac in position 11
decoding with 'cp936' codec failed
```

**根因**：`requirements.txt` 是 UTF-8 **无 BOM**，而 pip 24.0 的 `auto_decode()` 在没有 BOM 时回退到系统 locale（中文 Windows = GBK），于是带中文注释的文件直接解码失败。

**影响**：资料包最重要的一条安装命令，在中文 Windows 上 100% 失败。用户会以为"文件坏了"。

**规避**：`set PYTHONUTF8=1` 后再执行（UTF-8 模式会让 `locale.getpreferredencoding()` 返回 UTF-8）。

**建议修复**：给 `requirements.txt` 加 UTF-8 BOM，或把注释改成英文；同时升级 pip（新版已改善）。

> ✅ **本报告已修复**：已给 `requirements.txt` 加上 UTF-8 BOM，并复测确认 —— 现在不加任何环境变量，`pip install -r requirements.txt` 可直接解析成功。

---

### 缺陷 2 · 冒烟测试在缺依赖时自己崩溃 🔴 阻塞级

```
File "冒烟测试.py", line 123, in check_dependencies
    print(f"  {c('✗', RED)} ...")
UnicodeEncodeError: 'gbk' codec can't encode character '\u2717'
```

**根因**：第 96 行只在「TTY 且非 NO_COLOR」时才去色，所以**颜色被正确关闭了**；但 `✗`(U+2717) 这类**符号本身**仍是非 ASCII，在 GBK 控制台打印即崩。

**讽刺之处**：崩的时机恰好是「检测到有库缺失」的那一刻 —— 也就是说，**最需要这份报告的时候它恰好交不出来**。装齐依赖时反而不崩。

**建议修复**：文件开头加 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`，或把 `✗ ✓ ⊘ ⏱` 换成 `[x] [v] [-] [!]` 之类的 ASCII 符号。

---

### 缺陷 3 · 子进程输出解码失败，导致失败原因全部丢失 🔴 阻塞级

```
Exception in thread Thread-33 (_readerthread):
UnicodeDecodeError: 'gbk' codec can't decode byte 0xae in position 82
```

**根因**：第 173-180 行的 `subprocess.run(..., capture_output=True, text=True)` **没有指定 `encoding`**。`text=True` 会用 locale 编码（GBK）去解码子进程的 UTF-8 中文输出，读取线程直接抛异常。

**后果**：`proc.stderr` 变成空字符串，冒烟测试只能报一句无信息的 `退出码 1`。**第一轮实测的 2 个失败，真实原因（`/bin/sh` 找不到、`fcntl` 不存在）完全被这层解码错误掩盖了** —— 我必须手动单独运行那两个脚本才查出根因。

**建议修复**：`subprocess.run(..., text=True, encoding="utf-8", errors="replace")`。

---

### 缺陷 4 · `requirements.txt` 缺 `pytest-asyncio` 🟠 影响结论可信度

`spiderkit/tests/test_spiderkit.py` 有 7 个 `@pytest.mark.asyncio` 异步测试，但依赖清单只列了 `pytest>=8.0`。

**现象**：这 7 个测试全部失败，报 `async def functions are not natively supported`；README 与「开始这里.md」都宣称 **55 passed**，按文档装依赖的用户只会看到 **7 failed**，会误判"资料包坏了"。

**佐证**：`spiderkit/pyproject.toml` 第 14-19 行的 `[project.optional-dependencies] dev` **确实写了** `pytest-asyncio>=0.24` —— 所以是顶层 `requirements.txt` 抄漏了，不是作者不知道。

**修复**：在 `requirements.txt` 组 2 里加 `pytest-asyncio>=0.24`。已验证：装上后 **55 passed**。

> ✅ **本报告已修复**：`requirements.txt` 已补入 `pytest-asyncio>=0.24`。

### 缺陷 5 · `requirements.txt` 缺 `typer` 🟡 功能不可用

`spiderkit/cli.py:16` 有 `import typer`，而 `pyproject.toml` 把 `typer>=0.12` 列为**正式依赖**（不是可选），但顶层 `requirements.txt` 没写。

**修复**：`requirements.txt` 补 `typer>=0.12`。已验证：装上后 CLI 导入成功。

> ✅ **本报告已修复**：`requirements.txt` 已补入 `typer>=0.12`。

### 缺陷 6 · 2 个脚本硬依赖 Unix，且全库零平台判断 🟠 Windows 兼容性

| 文件 | 报错 | 根因 |
|---|---|---|
| `stage6_distributed/64_deployment.py` | `FileNotFoundError: [WinError 2]` | 第 1951 行硬编码 `argv = ["/bin/sh", "-c", ...]`，Windows 无 `/bin/sh` |
| `stage6_distributed/65_distributed_practice.py` | `ModuleNotFoundError: No module named 'fcntl'` | 第 63 行 `import fcntl`，该模块仅 Unix 提供 |

**放大问题**：全库 49 个文件里，`sys.platform` / `os.name` / `platform.system` 的匹配数是 **0**。也就是说这两个脚本**没有任何优雅降级**，在 Windows 上必然硬崩，且冒烟测试也没把它们划入"平台不支持"分类，而是记成"失败"，误导用户以为代码有 bug。

**补充**：这两个脚本在 Linux 上大概率是正常的 —— `64_deployment.py` 讲 Docker 信号传递（本来就只能在 Unix 上演示），`65_distributed_practice.py` 用 `fcntl` 做文件锁。这属于**平台局限，不是代码错误**。

**修复建议**：文件顶部加平台守卫，例如
```python
if sys.platform == "win32":
    print("⚠ 本课依赖 Unix 的 /bin/sh 与 fcntl，请在 WSL / Linux / macOS 上运行")
    sys.exit(0)   # 退出码 0，避免被冒烟测试记成「失败」
```
`65_distributed_practice.py` 也可用 `msvcrt.locking` 做 Windows 等价实现。
