## 三、发现的缺陷（7 处，全部已修复）

### 缺陷 1 · `pip install -r requirements.txt` 在中文 Windows 上直接失败 🔴

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xac in position 11
decoding with 'cp936' codec failed
```

**根因**：`requirements.txt` 是 UTF-8 **无 BOM**，pip 的 `auto_decode()` 在无 BOM 时回退到系统 locale（中文 Windows = GBK），带中文注释的文件直接解码失败。

**影响**：资料包最重要的一条安装命令，在中文 Windows 上 100% 失败，用户会以为文件坏了。

> ✅ **已修复**：给 `requirements.txt` 加 UTF-8 BOM。复测确认——不加任何环境变量，`pip install -r requirements.txt` 可直接解析成功。
> （同时把 pip 从 24.0 升级到 **26.2.1**。）

---

### 缺陷 2 · 冒烟测试在缺依赖时自己崩溃 🔴

```
File "冒烟测试.py", line 123, in check_dependencies
    print(f"  {c('✗', RED)} ...")
UnicodeEncodeError: 'gbk' codec can't encode character '\u2717'
```

**根因**：脚本只在「TTY 且非 NO_COLOR」时才去色，颜色确实关掉了；但 `✗`(U+2717) 这类**符号本身**仍是非 ASCII，在 GBK 控制台打印即崩。

**讽刺之处**：崩的时机恰好是「检测到有库缺失」的那一刻 —— **最需要这份报告的时候它恰好交不出来**。装齐依赖时反而不崩，所以作者在 Linux 上永远不会遇到。

> ✅ **已修复**：脚本开头把 `sys.stdout` / `sys.stderr` 重配为 UTF-8，并允许 `errors="replace"` 降级。

---

### 缺陷 3 · 子进程输出解码失败，失败原因全部丢失 🔴

```
Exception in thread Thread-33 (_readerthread):
UnicodeDecodeError: 'gbk' codec can't decode byte 0xae in position 82
```

**根因**：`subprocess.run(..., capture_output=True, text=True)` **没指定 `encoding`**。`text=True` 用 locale 编码（GBK）解码子进程的 UTF-8 中文输出，读取线程直接抛异常。

**后果**：`proc.stderr` 变成空字符串，冒烟测试只能报一句 `退出码 1`。**第一轮实测的 2 个失败，真实原因（`/bin/sh` 找不到、`fcntl` 不存在）完全被这层解码错误掩盖** —— 必须手动单独运行那两个脚本才查得出根因。

> ✅ **已修复**：两处 `subprocess.run`（课程文件 + pytest）都补上 `encoding="utf-8", errors="replace"`，并通过 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1` 让子进程也以 UTF-8 输出。

### 缺陷 6 · 全包 49 个脚本在中文 Windows 控制台无一直能跑完 🔴【最严重】

这是本次检验最重要的发现，也解释了为什么前面的失败原因那么难定位。

```
# 直接运行任意一课，控制台代码页 936
UnicodeEncodeError: 'gbk' codec can't encode character '\xa3' ...   # 50_sql_basics.py  ￥符号
UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0' ... # 49_compliance.py ⚠符号
UnicodeEncodeError: 'gbk' codec can't encode character '\u2717' ... # 35_checkpoint.py ✗符号
```

**根因**：课程输出大量使用 `✓ ✗ ⚠ ▸ ✅ ❌` 等非 ASCII 符号，而 Windows 控制台默认 GBK（cp936），这些字符不在 GBK 字符集里 → 打印即崩。

**影响范围**：`code/` 下 49 个 `.py`，**38 个会被直接运行的课程脚本无一幸免**。课程作者在 Linux（UTF-8 环境）开发，这个类别的问题永远不会暴露。

**为什么之前「通过」**：因为冒烟测试修好后会给子进程传 `PYTHONIOENCODING=utf-8` —— 也就是**只有通过冒烟测试跑才没事，用户自己双击/命令行跑就崩**。这是最容易被漏掉的一类问题。

> ✅ **已修复**：给 38 个课程脚本的导入块之后统一注入自适应片段（幂等，带标记注释）：
> ```python
> # --- [Windows UTF-8 输出适配] ---
> import sys as _dsh_sys
> for _stream in (_dsh_sys.stdout, _dsh_sys.stderr):
>     try:
>         _stream.reconfigure(encoding="utf-8", errors="replace")
>     except (AttributeError, OSError, ValueError):
>         pass
> del _stream, _dsh_sys
> ```
> 复测确认：在代码页 936 的控制台、**不设任何环境变量**，原先崩溃的脚本现在全部退出码 0 且中文正常显示。
>
> **为什么不用 `errors="replace"` 保留 GBK**：实测对比过 —— 保留 GBK 会让中文变乱码、符号变 `?`；切到 UTF-8 则中文和符号全部正确。对照见第六节。
>
> **为什么 `spiderkit` 库模块不注入**：库不应该改宿主的 stdout，这是坏实践。它只被 import、不被直接运行，天然不会触发该问题。
>
> **注意** `deploy/healthcheck.py` 未注入：它由 `64_deployment.py` 的 `render_healthcheck_py()` 自动生成，且只在 Linux 容器内运行，注入会被生成器覆盖、也没有必要。

### 缺陷 7 · 2 个脚本硬依赖 Unix，且全库零平台判断 🟠

| 文件 | 报错 | 根因 |
|---|---|---|
| `stage6_distributed/64_deployment.py` | `FileNotFoundError: [WinError 2]` | 硬编码 `argv = ["/bin/sh", "-c", ...]`，Windows 无 `/bin/sh` |
| `stage6_distributed/65_distributed_practice.py` | `ModuleNotFoundError: No module named 'fcntl'` | `import fcntl`，该模块仅 Unix 提供 |

**放大问题**：全库 49 个文件里，`sys.platform` / `os.name` 的匹配数是 **0** —— 两个脚本**没有任何优雅降级**，在 Windows 上必然硬崩。且原冒烟测试把它们记成「失败」而非「平台不支持」，误导用户以为代码有 bug。

这属于**平台局限而非代码错误**：`64_deployment.py` 讲 Docker 信号传递（本就只能在 Unix 演示），`65_distributed_practice.py` 用 `fcntl` 做文件锁。

> ✅ **已修复**：
> 1. `64_deployment.py`：`main()` 开头加 `sys.platform == "win32"` 守卫，打印明确说明后正常返回。
> 2. `65_distributed_practice.py`：`import fcntl` 改为 `try/except ImportError` 降级，`__main__` 处检测到 `fcntl is None` 时打印说明并正常退出。
> 3. `冒烟测试.py`：新增 `requires_unix()` 静态识别，把这类文件归入「跳过：仅 Unix」而不是「失败」。
>    注意此处**不能复用 `import_names()`** —— 它按 `sys.stdlib_module_names` 过滤标准库，而 `fcntl`/`termios` 恰恰是「Unix 独有的标准库模块」，复用会漏判。已改为直接走 AST 扫描。
