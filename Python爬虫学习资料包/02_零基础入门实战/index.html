!先看法律边界（重要，别跳过）

技术之前先讲规矩。这一节决定你接单时会不会踩雷。

很多教程把这一节放在最后当免责声明，我觉得那是本末倒置。你是奔着接单去的，客户找上门时，能不能做比会不会做更重要 —— 判断错了，轻则白干，重则惹上官司。

三条红线，碰了别接

🚫 绝对不要碰
  • 个人信息：手机号、身份证、住址、人脸、简历。这是《个人信息保护法》重点打击对象，爬了就是违法，没有模糊空间。
  • 需要登录才有权看的内容：绕过账号权限去爬付费课程、内部数据、私人朋友圈 —— 属于"非法获取计算机信息系统数据"。
  • 破坏性操作：批量注册、刷单、撞库、抢购、发垃圾评论。这些不是爬虫，是攻击行为。
⚠️ 灰色地带，接单前必须确认
  • 对方明确写了 robots.txt 禁止的目录
  • 网站服务条款（ToS）里写明禁止"自动化抓取"
  • 数据本身有版权（比如电商的商品图、文章全文）
  • 高频请求会影响对方服务器正常运行

实操上，我给自己定的判断流程是这样的：

检查项怎么查红灯信号
数据是否公开 不登录、无 Cookie 能不能看到？ 必须先注册登录
robots.txt 访问 网站/robots.txt 目标路径被 Disallow
是否含个人信息 看数据字段 出现姓名+联系方式组合
数据量级 估算总请求数 百万级、需要多 IP 轮换
对方态度 看 ToS / 有无官方 API 有官方 API 却让你硬爬
✅ 一个稳妥的底线

只爬不登录就能看到的公开数据，控制频率不干扰对方服务，不转售原始数据。满足这三条，绝大多数商业采集需求你都能接，风险也可控。另外 —— 有官方 API 就用 API，既稳定又快，客户也更认可。

💡 接单时一个保命习惯

把「合规判断」写进报价单。例如："本项目仅采集公开可见的商品价格信息，不含用户隐私数据，采集频率控制在每秒 1 次以内。" 白纸黑字写清楚，既是给客户说明，也是给自己留证据。

1爬虫到底是什么

五分钟建立正确的心智模型，比急着写代码重要得多。

剥掉所有技术术语，爬虫就是一个自动化的小助手，替你完成这三件事的循环：

📥
1. 请求

向网站服务器说"请把这个页面给我"。本质上和你在浏览器地址栏敲回车没有区别。

🔍
2. 解析

从返回的一大堆 HTML 里，精准定位你要的那几个字段：标题、价格、日期。

💾
3. 保存

把散落的数据整理成表，存成 CSV / Excel / 数据库，变成能用的资产。

然后循环第 1 步去处理下一页、下一个商品、下一个关键词。就这么多。你在后面几周学到的所有东西 —— 反爬、并发、动态渲染 —— 都是在解决这三步中某一环变得困难的问题。

浏览器里发生了什么

理解这个过程，能帮你解释后面 90% 的报错。当你在浏览器输入网址并回车：

  1. 浏览器向对方的服务器发出一个 HTTP 请求，里面带着你的身份信息（User-Agent、Cookie）。
  2. 服务器检查这个请求，决定给你什么。如果认识你、允许你访问，就返回状态码 200 和页面内容。
  3. 如果它认为你是机器人或请求太频繁，可能返回 403（拒绝）或 429（太频繁）—— 这就是"被反爬了"。
  4. 浏览器拿到 HTML 后，如果里面有 JavaScript，还会再执行一遍，把数据"渲染"出来显示给你。

爬虫要做的就是模仿第 1-3 步，而第 4 步是新手最容易掉进的坑 —— 这也是为什么后面要专门讲 Playwright。

两种技术路线，先认清再动手

对比项静态页面路线动态页面路线
核心工具requests + BeautifulSoupPlaywright

难度⭐ 简单⭐⭐⭐ 中等
占比约 70% 的场景约 30% 的场景
🔑 怎么判断该用哪种？

打开目标网页，按 F12 打开开发者工具，切到 Network 面板，刷新页面，看 Doc 类型请求的 Response —— 如果里面直接能看到你要的数据，就用 requests；如果是一堆看不懂的 JS 代码或空标签，就得用 Playwright。

💡 一个反直觉的事实

新手总以为爬虫难在"破解反爬"。实际上，80% 的失败是因为选择器写错（网页结构和你以为的不一样），剩下 15% 是编码问题。真正的反爬对抗，在商业项目里占比其实不高 —— 大多数甲方要的是公开数据。先把基础打牢，比研究奇技淫巧有用。

2.2 变量与数据类型

变量就是个贴了标签的盒子，你把数据放进去，之后用标签名就能取出来。Python 不需要声明类型，直接赋值：

基础语法.py
# 字符串：文字，用引号包起来
name = "三体"
url = "https://example.com"

# 整数和浮点数：数字，注意不能加引号
count = 42
price = 51.77

# 布尔值：真/假，用于判断
is_in_stock = True

# 列表：一串有序的数据，用方括号。爬虫用它存"多本书"
prices = [51.77, 53.74, 50.10]

# 字典：一对一映射，用花括号。爬虫用它存"一本书的多个字段"
book = {
    "title": "三体",
    "price": 51.77,
    "rating": 5,
}

# 取值方式：列表用下标（从 0 开始！），字典用 key
print(prices[0])        # 51.77 —— 第一个元素
print(book["title"])   # 三体

# 字符串常用操作
print("£51.77".replace("£", ""))  # "51.77" —— 去掉货币符号
print(float("51.77"))              # 51.77 —— 字符串转数字
print("  abc  ".strip())           # "abc" —— 去掉首尾空格
⚠️ 新手最常踩的三个坑
  1. 列表下标从 0 开始：prices[0] 是第一个，不是第二个。
  2. 字典的 key 必须用引号：book["title"] ✅，book[title] ❌（后者会被当成变量）。
  3. 字符串加减要注意类型："1" + 1 会报错，得写 int("1") + 1。爬来的数据几乎都是字符串，转换类型是家常便饭。

2.3 循环：爬虫的心脏

爬虫的本质就是"对一堆东西重复做同一件事"，所以循环是绝对核心。

循环.py
# for 循环：遍历一个列表，逐个处理
pages = [1, 2, 3]
for page in pages:
    print(f"正在采集第 {page} 页")
# 输出：正在采集第 1 页 / 第 2 页 / 第 3 页

# range() 生成一串数字，爬虫翻页最常用
for page in range(1, 4):
    print(page)          # 1 2 3（注意：不含 4！左闭右开）

# 遍历字典
book = {"title": "三体", "price": 51.77}
for key, value in book.items():
    print(f"{key} = {value}")

# enumerate：同时拿到下标和值，打印列表时很好用
for i, p in enumerate(pages, start=1):
    print(f"第 {i} 个：{p}")

你会在代码里频繁看到 f"..." 这种字符串，叫做 f-string，是格式化输出最方便的方式：用 {} 把变量嵌进去即可。

2.4 判断与函数

函数与判断.py
# if / elif / else：根据条件走不同分支
status = 200
if status == 200:
    print("采集成功")
elif status == 404:
    print("页面不存在")
elif status in (403, 429):
    print("被反爬拦截了")
else:
    print(f"其他情况：{status}")

# 判断"有没有"
if "title" in book:        # 字典有没有这个 key
    print(book["title"])
if prices:                     # 列表非空就是 True
    print("有数据")

# 函数：把一段逻辑打包，起个名字反复用
def clean_price(raw: str) -> float:
    """把 "£51.77" 这样的文本转成数字 51.77。

    Args:
        raw: 原始价格文本

    Returns:
        清理后的浮点数
    """
    return float(raw.replace("£", "").strip())

print(clean_price("£51.77"))   # 51.77

🔑 关键点：response 不是网页本身

requests.get() 返回的是一个 Response 对象，像个快递包裹 —— 里面装着状态码、响应头、正文等一堆信息。真正的网页内容在 response.text 里。 新手常犯的错是拿 response 直接去解析，然后困惑为什么报错。

3.2 状态码：读懂服务器的态度

状态码是服务器对你的回应，必须先看它再谈解析。这是新手最容易忽略的一步，也是排查问题的第一把钥匙。

状态码含义你该怎么办
200成功正常，继续解析
301 / 302重定向requests 会自动跟随，一般不用管
403禁止访问被识别为机器人 → 加 User-Agent（第 6 节）
404页面不存在URL 写错了，重试没意义，去检查链接
429请求太频繁限流了 → 加大延迟、降低并发
500 / 502 / 503服务器错误是对方的问题，等待后重试
🔑 一个必须养成的习惯

你在第 9 节的工程模板里会看到 resp.raise_for_status()。它的作用是：只要状态码不是 2xx 就立刻抛异常，而不是让程序带着一个 403 的错误页面继续往下解析，最后产出一堆空数据。宁可早点报错，也不要静默地产出错误结果。

3.3 编码：中文乱码的元凶

这是零基础学习者最困惑的问题之一："我明明抓到了中文，为什么打印出来是乱码？"

原因很简单：网页的二进制内容需要用某种编码规则翻译成文字，如果翻译规则用错了，就是乱码。requests 会自动猜，但经常猜错，尤其对国内网站。

编码处理.py
response = requests.get(url, timeout=10)

# 手动指定编码，再用 .text 就不会乱码了
# apparent_encoding 是 requests 根据内容推测的编码
response.encoding = response.apparent_encoding

# 顺序很重要：必须先设置 encoding，再访问 .text
# 因为 .text 一旦被访问，内容就已经用旧编码解码并缓存了
html = response.text
⚠️ 一个隐蔽的顺序陷阱

response.text 是惰性的：第一次访问时它才解码并缓存结果。如果你先写了 print(response.text) 再设置 response.encoding，第二次取还是乱码 —— 因为用的还是第一次的缓存。务必先设置 encoding，再碰 .text。

如果 apparent_encoding 仍然猜错（少数情况），直接指定：国内老网站常用 response.encoding = "gbk"，现代网站基本都是 "utf-8"。

3.4 该有的防护：timeout

超时设置.py
# ❌ 危险：没有 timeout，网络卡住时脚本会永远挂在那里
resp = requests.get(url)

# ✅ 正确：10 秒没响应就报错，脚本继续往下走
resp = requests.get(url, timeout=10)
🚫 这是我见过的最高频低级错误

新手写的爬虫在半夜挂掉，80% 是因为没加 timeout。requests 默认是无限等待 —— 对方服务器不响应，你的脚本就一直等，等到天亮，什么也没采到，连报错都没有。从第一个爬虫开始就养成加 timeout 的习惯，这比学什么高级技巧都值钱。

4把数据抠出来

从"看到页面"到"拿到字段"，这是爬虫真正产生价值的一步。

上一节你拿到了 HTML，但那是一坨给人看的文本。这一节要把它变成结构化的数据：书名、价格、评分，一行一条，可以直接进 Excel。

4.1 先学会用浏览器的"开发者工具"

这是整个教程里最重要的技能，没有之一。写爬虫 80% 的工作是"找到元素在 HTML 里的位置"，而这件事只能靠 F12 完成。

  1. 在目标页面按 F12（Mac 是 Cmd+Option+I），打开开发者工具。
  2. 点击左上角的箭头图标（或按 Ctrl+Shift+C），进入元素选择模式。
  3. 把鼠标移到页面上你想要的数据上（比如某个书名），点击它。
  4. 右侧 Elements 面板会自动高亮对应的 HTML 标签 —— 这就是你要在代码里定位的东西。
🔑 关键一步：右键 → Copy → Copy selector

找到目标标签后，右键点击它 → Copy → Copy selector，浏览器会直接给你一段 CSS 选择器。但不要无脑用 —— 它通常给的是最长最脆弱的路径（比如 body > div:nth-child(3) > ...），页面稍一改动就失效。你要做的是理解它、然后简化它，用 class 名这种稳定的特征去定位。

4.2 两个选择器方法，覆盖全部场景

方法返回什么时候用
soup.select()列表（可能为空）找一批元素，比如所有书
soup.select_one()单个元素或 None找唯一元素，比如书名

选择器语法跟你写的 CSS 一模一样，掌握这几种就够用了：

选择器语法速查
article.product_pod     # class 为 product_pod 的 article 标签
p.price_color           # class 为 price_color 的 p 标签
h3 a                    # h3 里面的所有 a 标签（空格表示"后代"）
p.instock.availability  # 同时有 instock 和 availability 两个 class
# 注意：选择器返回的永远是列表，即使只有一个结果
#       select_one 才返回单个元素

4.3 完整实战：抓取一页所有书

下面这段代码是实测跑通的，抓到了 20 本书的完整数据：

d02_parse_books.py已实测通过
import requests
from bs4 import BeautifulSoup

url = "https://books.toscrape.com/"
response = requests.get(url, timeout=10)
response.encoding = response.apparent_encoding

# 把 HTML 文本包装成可查询的对象
soup = BeautifulSoup(response.text, "html.parser")

# 找到所有书：每本书是一个 article.product_pod
books = soup.select("article.product_pod")
results = []

for book in books:
    # 书名藏在 title 属性里，用 ["title"] 取值
    title = book.select_one("h3 a")["title"]

    # 价格在文本里，形如 "£51.77"，要清理+转数字
    price = float(
        book.select_one("p.price_color").text.replace("£", "").strip()
    )

    # 评分藏在 class 里：class="star-rating Three"
    # ["class"] 返回列表 ['star-rating', 'Three']，取第二个
    rating_word = book.select_one("p.star-rating")["class"][1]
    rating_map = {"One": 1, "Two": 2, "Three": 3,
                  "Four": 4, "Five": 5}
    rating = rating_map[rating_word]

    results.append({
        "书名": title,
        "价格(£)": price,
        "评分": rating,
    })

for i, item in enumerate(results[:5], start=1):
    print(f"{i}. {item['书名'][:45]:<47} £{item['价格(£)']}")

6.3 重试机制：让脚本自己扛过抖动

网络偶尔抽风是常态。没有重试机制的爬虫，跑到第 800 条时因为一次超时整个崩掉，前面的工作全白费 —— 这是接单最尴尬的事故。

指数退避重试核心技巧
import time, random

def fetch(session, url, max_retries=3):
    """带指数退避重试的请求。

    第 1 次失败等 1 秒，第 2 次等 2 秒，第 3 次等 4 秒。
    加上随机抖动，避免多个任务同时重试形成"惊群"。
    """
    for attempt in range(1, max_retries + 1):
        try:
            resp = session.get(url, timeout=15)
            if resp.status_code == 404:
                return None          # 404 重试没意义，直接放弃
            resp.raise_for_status()
            resp.encoding = resp.apparent_encoding
            return resp.text
        except requests.RequestException as exc:
            wait = 2 ** (attempt - 1) + random.uniform(0, 0.5)
            print(f"第 {attempt} 次失败：{exc}，{wait:.1f}s 后重试")
            if attempt < max_retries:
                time.sleep(wait)
    return None   # 重试耗尽
🔑 什么错误值得重试？

这是区分新手和老手的关键：

  • 值得重试：超时、连接错误、500/502/503（对方服务器临时故障）、429（等久一点再来）
  • 不该重试：404（页面真不存在）、403（被明确拒绝，重试还是被拒）

无脑重试所有错误，只会浪费时间并加重对方负担。

6.4 关于"更高级的反爬"，我想说点实话

💡 别急着学 JS 逆向

网上很多教程一上来就讲 JS 逆向、字体加密、滑块验证码 —— 这些内容看着很酷，但对你现在的阶段弊大于利：

  • 它们只适用于极少数"高价值防御站"，而这类站往往爬了就有法律风险，接单纯属给自己找麻烦。
  • 真正能在市场上稳定接到的单，80% 是公开数据 + 中等防御，靠本节的 UA + 延迟 + 重试就能搞定。
  • 逆向技术迭代极快，今天学的明天可能就失效，投入产出比低。

正确的顺序：先把"稳定采集公开数据"做扎实 → 能接单赚钱 → 遇到真正需要逆向的项目时，再针对性学。而不是为了炫技去啃硬骨头。

⚠️ 遇到验证码怎么办？

三个选择，按推荐排序：① 降速 —— 很多验证码就是因为你请求太快才触发的，慢下来就没事了；② 换时机 —— 分散到不同时段；③ 老实告诉客户这个站防得严，建议改用官方 API。不要去找打码平台绕过验证码 —— 那已经从"数据采集"滑向"对抗系统安全"了，性质完全不同。

7动态页面 Playwright

当 requests 抓回来是空壳时，你需要一个真正的浏览器。

这是很多人卡住的地方：F12 里明明能看到数据，requests 抓回来却是空标签。不是你写错了，是数据根本不在初始 HTML 里 —— 它由 JavaScript 在页面加载后动态生成。

7.1 三秒判断法

🔑 判断是不是动态页面的最快方法
  1. 浏览器里按 Ctrl+U（Mac: Cmd+Option+U）查看网页源代码 —— 注意这不是 F12 里的 Elements 面板！
  2. 在这个源代码里搜你要的数据（比如某个商品名）。
  3. 搜得到 → 静态页面，用 requests。搜不到 → 动态渲染，用 Playwright。

原理：F12 的 Elements 面板显示的是JS 执行后的最终状态，而 Ctrl+U 显示的是服务器返回的原始内容。requests 拿到的就是后者。

    """用无头浏览器抓取动态渲染后的 HTML。"""
    async with async_playwright() as p:
        # headless=True 不弹窗口；调试时改成 False 能看见浏览器操作
        browser = await p.chromium.launch(headless=True)

        context = await browser.new_context(
            viewport={"width": 1920, "height": 1080},
            user_agent=("Mozilla/5.0 (Windows NT 10.0; Win64; x64) "
                        "AppleWebKit/537.36 (KHTML, like Gecko) "
                        "Chrome/120.0.0.0 Safari/537.36"),

        await context.close()
        await browser.close()
        return html

7.3 Playwright 的三种"等待"策略

动态页面最大的坑是"等得不够" —— 页面还没加载完你就去取数据，结果当然是空的。三种等待方式，按可靠性排序：

方式写法适用可靠性
等元素出现 wait_for_selector(".item") 明确知道数据在哪个元素里 ⭐⭐⭐ 最推荐
等网络空闲 wait_until="networkidle" 不确定具体元素，数据来自接口 ⭐⭐ 常用
硬等 page.wait_for_timeout(3000) 实在没办法时的兜底 ⭐ 不推荐
⚠️ 别用 time.sleep() 等动态页面

新手常写 time.sleep(5) 然后取数据。问题是：你根本不知道 5 秒够不够。网速快时浪费 4.8 秒，网速慢时还是抓不到。应该用 wait_for_selector —— 元素出现了立刻继续，没出现就等，最多等到超时。又快又稳。

7.4 一个更聪明的选择：抓接口而不是抓页面

💡 遇到动态页面，先别急着上 Playwright

动态页面的数据通常来自一个 XHR / Fetch 请求（浏览器向服务器要数据的接口）。直接抓那个接口，比用 Playwright 渲染页面快 10 倍、稳定得多、也不需要浏览器。

怎么找：F12 → Network → 筛选 Fetch/XHR → 刷新页面 → 逐个点开看 Response，找到返回 JSON 数据的那个请求。然后你又可以用回 requests 了 —— 只是访问的是接口地址，拿回来的是 JSON。

优先级：能抓接口就抓接口，接口抓不到才上 Playwright。 这是很能体现水平的一个判断。

8并发加速

把 35 秒的活压到 8 秒 —— 但要知道边界在哪。

单线程爬虫的效率瓶颈不是 CPU，也不是网速，而是"等待"。每次请求要等服务器响应 0.5 秒，这期间你的 CPU 完全在睡觉。1000 个页面就是 500 秒的纯等待。

并发的本质就是让这些等待重叠起来 —— 趁着等 A 的响应的间隙，去请求 B 和 C。

8.1 线程池：最容易上手的方案

Python 并发有几种方式（多线程 / 多进程 / asyncio），对爬虫这种IO 密集型任务，线程池最平衡：比 asyncio 好懂，比多进程轻量。

d06_concurrent.py已实测通过
import time, random
from concurrent.futures import ThreadPoolExecutor, as_completed

MAX_WORKERS = 5   # 并发数：从 5 开始，被限流就降到 3

def fetch_and_parse(page: int):
    """抓取并解析单页，供线程池调用。"""
    url = f"https://books.toscrape.com/catalogue/page-{page}.html"
    # ⚠️ 每个线程用独立的 Session，共享 Session 高并发下会出问题
    session = requests.Session()
    session.headers.update(HEADERS)
    try:
        resp = session.get(url, timeout=15)
        resp.raise_for_status()
        resp.encoding = resp.apparent_encoding
    except requests.RequestException as exc:
        print(f"✗ 第 {page} 页失败：{exc}")
        return page, []
    # ... 解析逻辑
    time.sleep(random.uniform(0.2, 0.6))  # 随机延迟打散节奏
    return page, books

# 关键：用 with 管理线程池，退出时自动等待所有任务完成
with ThreadPoolExecutor(max_workers=MAX_WORKERS) as executor:
    # submit 提交任务，立刻返回 Future（未来结果的凭据）
    futures = {executor.submit(fetch_and_parse, p): p
               for p in range(1, 21)}

    # as_completed：谁先完成先处理，不用按提交顺序干等
    for future in as_completed(futures):
        page, books = future.result()
        all_books.extend(books)

8.2 并发数开多少？这是个需要克制的问题

🚫 并发不是越大越好

这是我必须强调的一点。把并发开到 50、100，等于对别人服务器发起小型攻击 —— 后果是 IP 被封、甚至可能被追究责任，而且你自己的成功率反而更低（大量请求被拒）。

经验值：

  • 3-5 线程：稳妥区间，适合绝大多数接单项目
  • 10 线程：上限，只有在对方站点性能好、且你测试过没触发限流时才用
  • 超过 10：不要。真要大规模采集，应该走"多机分布式 + 代理池"的正规路子，而不是在一台机器上猛灌。

8.3 并发的三个坑

🔒
共享对象不安全

多线程共享一个 Session 或列表会出问题。Session 要每个线程独立，写列表要用锁或让主线程统一收集。

📉
顺序不再可靠

并发完成的顺序不等于提交顺序。如果需要有序，记得带页码排序，或者用 executor.map。

🐛
报错更难定位

某个线程崩了，堆栈信息可能很乱。务必在每个任务内部 try/except，记录清楚是哪个 URL 出的问题。

✅ 什么时候该用并发？

页数超过 100 页时值得上并发。几十页的小任务，老老实实单线程加延迟，代码简单不易出错，维护成本更低。不要为了炫技把简单的事搞复杂。

from dataclasses import dataclass, asdict

@dataclass
class Book:
    """一本书的标准化数据模型。

    用 dataclass 而非裸字典的好处：
      - 字段名写错会立刻报错，不会静默产出脏数据

    """
    title: str
    price: float
    rating: int
    stock: int
    url: str

    @property
    def key(self) -> str:
        """唯一标识，用于去重。"""
        return self.url

② 断点续爬：最值钱的一个特性

断点续爬核心实测有效
class Checkpoint:
    """记录已完成的页码，支持中断后继续。"""

    def __init__(self, path):
        self.path = path
        self.done_pages = set()
        self.books = {}
        self._load()        # 启动时尝试恢复进度

    def _load(self):
        """从磁盘恢复进度。"""
        if not self.path.exists():
            return
        raw = json.loads(self.path.read_text(encoding="utf-8"))
        self.done_pages = set(raw.get("done_pages", []))
        self.books = {k: Book(**v) for k, v in raw.get("books", {}).items()}

    def save(self):
        """把进度写到磁盘。"""
        payload = {
            "done_pages": sorted(self.done_pages),
            "books": {k: asdict(v) for k, v in self.books.items()},
        }
        self.path.write_text(
            json.dumps(payload, ensure_ascii=False, indent=2),
            encoding="utf-8",
        )

# 主循环里：跳过已完成的页
for page in range(1, TOTAL_PAGES + 1):
    if page in checkpoint.done_pages:
        logger.info("第 %d 页已完成，跳过", page)
        continue
    # ... 采集这一页
    checkpoint.add(page, books)
    checkpoint.save()   # 每页都存，最坏只丢一页

🔑 这是学生代码和商业代码的核心分界线

学生代码遇到一条异常数据就崩了。商业代码会记录、跳过、继续。

⑤ 优雅退出：Ctrl+C 也要保住成果

信号处理
import signal, sys

class GracefulExit:
    """捕获 Ctrl+C，先把进度存好再退出。"""

    def __init__(self, checkpoint):
        self.checkpoint = checkpoint
        # 注册信号处理器
        signal.signal(signal.SIGINT, self._handler)

    def _handler(self, signum, frame):
        logger.info("收到中断信号，正在保存进度……")
        self.checkpoint.save()
        logger.info("进度已保存，下次运行将自动续爬")
        sys.exit(0)

用户体验上的差别：没有这个，客户按 Ctrl+C 后得从头再来；有了它，按完之后重新运行，脚本说"我从上次的地方继续"。

A排错速查

遇到报错先来这里查，90% 的问题都在表里。

报错 / 现象原因解决办法
TypeError: 'NoneType' has no attribute 'text' select_one() 没找到元素，返回 None 检查选择器；print() 出来看是不是 None；确认是否动态页面
requests.exceptions.ConnectionError 网络不通 / 域名写错 / SSL 问题 检查 URL；浏览器能否打开；verify=False 测试（仅调试用）
requests.exceptions.ReadTimeout 服务器响应超时 加大 timeout 值；加重试机制
状态码 403 被识别为机器人 加 User-Agent 请求头；降低请求频率
状态码 429 请求太频繁被限流 加大 sleep 间隔；降低并发数；换个时间再来
抓到的中文是乱码 编码设置错误 response.encoding = response.apparent_encoding，再取 .text
Excel 打开 CSV 中文乱码 缺少 BOM 头 写文件时用 encoding="utf-8-sig"
抓回来是空壳 / 没有数据 动态渲染页面 用 Playwright，或直接抓 XHR 接口（见第 7 节）
数据比预期少很多 分页没处理完 / 部分请求失败被跳过 打印每页结果数；检查失败日志；加大重试
脚本跑着跑着卡住不动 没设 timeout 所有请求都加 timeout=15
SSLError 证书验证问题 更新 certifi：pip install --upgrade certifi
并发后数据错乱 / 丢失 线程共享了 Session 或列表 每个线程独立 Session；主线程统一收集结果

通用排错三步法

  1. 先看状态码 —— 是不是 200？不是的话，问题在请求阶段，还轮不到解析。
  2. 再打印中间结果 —— print(response.text[:500]) 看拿到的是什么，print(soup.select_one("选择器")) 看选到了什么。
  3. 最后对比浏览器 —— 回到 F12，确认选择器和你以为的一致。
🔑 一条万能调试语句

想不清楚哪出问题时，把这行加在解析前：
print(response.status_code, response.text[:500])
80% 的问题看一眼就清楚了。 —— 因为你立刻能知道：请求成不成功、拿到的是什么内容。别急着改代码，先看清楚发生了什么。
